# 逻辑与 Agent 职责自审

用于新建、迭代和独立 Code Review。先审受影响的完整业务链，交付前按实际代码再审；用户要求全应用审查时覆盖所有入口、角色、Skill、工具、持久化和 Surface。只审查的请求不授权修复、发布或调用真实模型。

## 先建立事实，不给架构打形式分

读取需求、`application.yaml`、每个 Agent 的真实 instructions／Skill、工具及 Surface operation 的处理函数、数据提交点和对应测试。沿调用关系追踪，不用文件名、Agent 数量、提示词长度或关键词命中判定设计好坏。清单中存在一个角色不代表当前引擎真的能沿声明的委派链调用它。

复用 `APPLICATION_DESIGN.md` 记录业务链和本轮审查，不新增 manifest 字段或自造 Runtime 协议。每项核心需求至少有一条可追溯记录：

`入口 → 负责决策的角色 → Skill／HTTP 操作 → 真实 actor 的授权 → 数据提交 → 用户可核验结果`

外部调用需求必须有用户明确答案；需要时逐项追踪“CLI 命令 → 公开入口 → 后端授权 → 提交 → 命令结果”，对照确认清单检查缺项和额外开放项。CLI 不能复制业务规则或绕过后端授权，未实现 CLI 不能仅凭后端测试宣告完成。个人数据链还要核对轮次可见性和应用 ACL。

同时标出对象／版本、确认点、幂等键、失败后的可查询状态和恢复责任；没有该环节时说明不适用原因。确定性数据校验、授权与事务属于后端，不为了“AI 原生”再拆成 Agent。只有导航需求不额外生成总结；没有副作用的读取不机械加审批。

## 检查职责是否混乱

对每个角色回答：目标是什么、接收什么、交付什么、不负责什么、允许哪些工具／数据／模型能力、谁在失败时收尾。对照提示词、Skill 和代码，而不只核对设计文档。

- **需要拆分的迹象**：独立业务目标／产出；读与写或审批者的权限边界不同；独立上下文、状态、失败恢复或专业模型策略。说明拆分具体改善了什么，再改清单与调用方。
- **需要合并的迹象**：多个角色没有独立决策，只为一个函数或同一目标中的机械步骤互相交接。相同权限、上下文、生命周期的短流程可以由一个 Agent 和几个单一工具完成。
- **委派链**：逐条核对入口、实际可调用目标、输入／结果契约、失败与取消传递、谁负责最终回复。检验当前运行能力，不凭 YAML 推测支持嵌套、并行或恢复。没有调用入口的角色和循环转交需查清原因；直接由公开入口调用的角色不能误判成孤岛。
- **实际暴露能力**：检查编译后的工具、委派目标与 Skill 挂载，不只审清单；框架默认注入的通用 Agent 或共享 Skill 不能绕过白名单。并行选择要按持久选择 ID 恢复，不能以返回顺序猜目标。
- **隐藏编排**：Skill 是否偷偷变成另一角色、授予新权限；工具是否暗中选择模型、决定业务阶段或执行未展示的整条流程。Skill 是方法，后端是校验与执行，不是绕过 Agent 策略的旁路。
- **状态**：从合法入口能否到达每个必要阶段；失败、取消、等待确认后能否继续或明确结束；工具失败是否被转成成功、空列表或“已完成”。持续会话不必有终止阶段，阶段循环也不自动等于错误，必须结合真实转移规则判断。

例如“检索并解释资料”可能是一个内聚角色；“检索资料并管理全组织的发布权限”必须重新审查权限与职责。把查列表、读详情各拆一个角色并不天然更合理。不得把这些例子硬编码成固定 Agent 模板。

## 用反例走完整业务链

选择适用场景并连接实际入口和持久化状态，不要求没有相关功能的应用实现空功能：

| 风险 | 必须观察的结果 |
| --- | --- |
| 角色或工具交接失败 | 调用者得到明确失败；没有假成功、丢失收尾责任或无限转交 |
| 读取失败／授权撤回 | 错误不冒充空数据；禁止继续依赖错误结果写入或扩大范围 |
| 取消／无回应／范围改变 | 未确认操作不执行；已开始的外部操作须等待收敛或查询真实状态，不能将取消等同回滚；需要时重新预览确认；详见 [确认规则](confirmation-and-chat.md) |
| 重复请求／提交后响应丢失 | 查询同一操作结果，副作用不重复；不根据超时推断“未提交” |
| 跨 actor／实例／组织 | 当前后端授权拒绝；共享关系不能变成跨实例权限 |
| 重启／迁移／部分失败 | 读取真实存储、识别未完成状态，有明确恢复或人工处理方式 |
| 模型成功但产物保存失败 | 保留网关调用和结算回执；报告交付失败而非模型失败，不重新生成以冒充下载重试 |
| Surface 切换实例／请求乱序 | 旧响应不覆盖新实例；提交后重取数据；要求 ACK 的命令未确认不能称已完成 |

测试适配器必须调用被测行为，不能自己补权限、确认、恢复或返回预期结果。检查测试是否真的会失败：在临时副本里故意破坏一个高风险不变量（例如取消仍写入、重复提交重复执行、跨实例读取），运行对应 suite，确认其失败，再用未破坏版本复跑。禁止在用户工作区或生产数据上做故障注入；不把 mutation 留在交付物中。

## 工具证据和语义结论分开

执行 [官方验证与门禁](verification.md) 及 [app test](application-tests.md)。核对同一应用版本／source_digest、退出码、必要 checks、suite 和 required_cases、未运行 coverage。修复后重新生成证据，不能拼接修改前的 full 与修改后的业务测试宣称同一版本通过。

先完成应用内设计记录和源码修改，再运行最终验证；命令报告、日志和验收记录写在应用树外。验证后修改应用内文档同样会改变摘要，必须重跑，不能忽略这类变化。

- `static` 证明已实现的结构检查；不证明提示词与业务逻辑一致。
- `full` 证明构建与启动；不证明业务、角色协作、真实模型或目标安装。
- `app test` 证明当前 suite 的实际断言；把同一合同测试改名为 business 不产生业务覆盖。
- 自审由 Coding Agent 根据源码与反例作出，不能由脚本计数得出“职责清晰”。固定模型测试不等于真实模型验收，测试自报结果也不是不可伪造的证明。

复杂或高风险改动且可用子 agent 时，让独立审查者读取需求、Skill 和原始工程，不提供预期答案。比较其实际发现和证据，再修正；没有独立审查能力时如实标记自审，不虚称双人通过。

## 交付记录

按严重程度列出可复现问题：触发条件、文件／行号、违反的业务不变量、用户影响和消除根因的修复方案；改动大小不作为质量目标，风格偏好不作阻断问题。记录本次拆分／合并／保留角色的理由、已修复问题和仍缺失的证据。

结论分别给出：结构与构建、业务测试、职责／逻辑审查、真实模型／服务联调、目标安装。默认整体通过必须满足 [注册后最小验收](target-smoke.md)，有前端时基础浏览器验证不得省略；必要项未运行／阻塞不能整体通过。使用通过／失败／未运行／不适用（附理由）；遇到数据损失、越权、假成功或关键需求未闭环不能写“整体完成”。不为漂亮结论删测试、降低必要项、补兼容分支或扩权。
