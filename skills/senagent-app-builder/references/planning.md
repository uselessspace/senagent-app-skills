# 规划与技术选型

## 先问业务，再选语言

先读取已有工程和用户偏好。新应用仅收集缺少且会改变方案的信息：服务谁、核心动作与结果、已有团队语言、需要哪些解析／数据工具、部署架构、是否有界面、共享范围、敏感操作。

需求不足以判断选型时，先指出缺少的信息，提出少量与决策直接相关的问题，收到答复后确认理解，再给推荐；不要先生成 Python／Go 工程再补问。用户只说“做一个资料归档应用”时，不足以假设主要做文档解析：先确认资料格式、是否需提取／检索内容、已有技术栈及部署约束。已有明确答案就复用，不重复问卷。

| 条件 | 倾向 | 原因与代价 |
|---|---|---|
| 团队已有 Python／Go 工程与运维能力 | 延续现有语言 | 维护和集成成本通常比语言微小性能差异重要 |
| 文档处理、数据分析、科学计算，依赖主要在 Python 生态 | Python | 集成直接；需锁定 Python 与系统依赖，容器同步安装 |
| 以 HTTP、并发 I/O、结构化业务和长期服务为主，团队熟悉 Go | Go | 静态类型和二进制部署方便；核查所需库、cgo、资源和证书 |
| 快速验证、无既有语言偏好、两者生态均满足 | Python + FastAPI | 便于迭代；是 Builder 默认值，不是 Runtime 限制 |
| 团队明确追求应用后端单二进制交付且库支持 | Go | 仍可能有数据库、资源和 cgo 动态依赖，不承诺零依赖 |
| 主要成本来自远程模型延迟 | 不以语言性能作为决定性理由 | 两者调用同一 Runtime 模型能力，不直接决定模型质量或费用 |
| 只有 Java 技术栈 | 明确目前不支持 Java | 用户同意再选 Python／Go，不生成假 Java manifest |

向用户给出“建议语言 + 两条与需求相关的理由 + 主要代价”。存在真实权衡时问一个简短问题；用户已选定就直接推进。开发选型使用 Coding Agent 宿主交互，不在尚未存在的应用中调用 Runtime `request_choice`。

例如，确认需要解析 PDF／表格且没有既有技术栈后：“这些格式解析是主要工作，我建议 Python + FastAPI，便于复用解析库和类型化 HTTP 契约；代价是需要管理解释器与依赖。”这不是遇到“资料”二字就固定推荐 Python。

## 外部调用必须明确

新建时明确询问“是否需要其他系统、脚本或 Coding Agent 从外部调用这个应用？如果需要，哪些能力需要提供命令行调用？”已经给出的答案不重复问。需要时读取 [外部调用与应用 CLI](../../senagent-app-cli/references/external-cli.md)，先列出具体能力、权限、副作用及 CLI 交付方案，请用户确认范围，再与后端同步实现。不能把“需要外部调用”推断为“开放全部能力”；未回答保持待确认。

## 框架、数据库与前端默认值

| 场景 | 选择 | 何时不选 |
|---|---|---|
| Python HTTP 应用 | FastAPI + Uvicorn + Pydantic | 团队已有 Django 工程或确实需要其 Admin／完整 ORM 时选 Django；需要自己组装轻量 ASGI 原语时选 Starlette |
| Python 业务持久化 | SQLAlchemy 2 + Alembic | 尚无业务表时不预装；Django 工程使用自带 ORM 和 migration |
| Go HTTP 应用 | Gin | 用户已选定现有框架时沿用，不再并置第二套 router |
| Go 业务持久化 | GORM + 版本化迁移 | 尚无业务表时不预装 |
| 单机、单写入服务、小数据量 | SQLite | 持续并发写、多副本或需要独立数据库服务时直接选 PostgreSQL |
| 持久交互界面 | React + TypeScript + Vite | 纯 Chat 应用保持 `surfaces: []` |

数据库在设计时二选一。不为“以后也许扩容”同时实现 SQLite 和 PostgreSQL 适配器；达到升级条件时再用新迁移切换。TanStack Query 只用于服务端状态缓存与失效，TanStack Router 只用于多视图／深链，shadcn/ui 只按实际组件需求引入。

## 最小设计记录

在应用工程记录以下决策，建议用一页 `APPLICATION_DESIGN.md`，不塞入 Runtime manifest 的未知字段：

- ID／版本、语言及原因、用户、核心流程、非目标。
- 对象 ID／版本、状态、不变量、持久化、迁移与删除范围。
- instance／organization 数据 scope；新实例保持哪些内容为空；`agent_turn_visibility: instance|actor` 与个人数据进入模型、Chat、工作区和生成物的边界。
- 外部调用是否需要、用户确认的能力清单与排除项、调用者、CLI 命令映射与交付方式；尚待确认的范围不得默认补齐。
- actor／应用归属人／实例归属人的语义，以及应用自有业务角色／对象 ACL 矩阵。
- Agent 职责、Skill、工具、委派、模型逻辑能力。
- Chat／Surface 分工、选择场景、敏感操作确认与可信授权来源。
- 依赖、超时、目标平台、模型成本、验收与恢复方式；目标 SenAgent、注册／审批身份、测试实例与数据范围、最小模型预算和前后端验证路径，按 [注册后最小验收](../../senagent-app-verify/references/target-smoke.md) 确认。

将每项业务需求关联测试：需求 → 夹具 → 操作 → 业务断言 → 反例 → 实际执行证据。没有真实测试不要标记完成。

角色方案及每次能力变更按[逻辑与职责自审](../../senagent-app-review/references/self-review.md)记录拆分／合并／保留的依据；实现后再对照实际调用链复审，避免设计文档与代码脱节。

## 工程顺序

scaffold → 原始 full 基线 → 业务对象／授权／必要持久化 → 单个工具或 operation → Agent／应用内 Skill → 必要 Surface → 更多能力与角色 → 分层验收。

只引入当前业务链需要的 Agent、表、检索和 UI，先让一条真实业务链跑通。构建外部应用只依赖安装 CLI 与版本化公开协议，不依赖 SenAgent 源码。
