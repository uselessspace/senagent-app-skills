# Chat 选择和敏感操作确认

## 默认策略

删除（包括空分类）、永久删除、清空、覆盖已有成果、批量不可逆变更、对外发送、共享发布、权限变更默认先确认。管理员也不免确认。用户最初说“删除这些”表示任务意图；在具体对象和影响尚未展示时，不等于完成最终范围确认。

普通查询、打开、导航和无副作用预览不确认。明确的新增操作通常直接做。可逆编辑是否需要确认依影响决定；例外须由产品明确设计并测试，不能由模型临时省略。对同一已展示、未变更范围的明确确认不反复追问；用户修改对象、数量、版本、接收人或可见范围则重做确认。

## Chat 协议的真实限制

当前 Agent 的 `request_choice` 工具只接受 `question`、`options`、`allow_multiple`、`context`。它自动生成 choice ID 并暂停。**工具没有 `allow_custom_response` 参数，也没有默认选中项参数**；虽然 ChoiceRequest 数据模型有 allow_custom_response，不能据此给工具传不存在的参数。Runtime 允许用户自由填写 Other。

确认选项用单选、稳定 ID。把取消放在第一项作为安全呈现建议，但这不是“默认取消已提交”；必须等真实选择返回。不要增加倒计时自动确认或无响应自动执行。

下面是工具参数示例，对象来自本轮后端预览，不是业务 HTTP Schema：

```json
{
  "question": "永久删除《项目草稿》和《会议记录》共 2 份文档？原文、派生图片与相关索引将被删除且无法撤销；其他文档不受影响。",
  "options": [
    {"id": "cancel_delete", "label": "取消", "description": "保留全部文档"},
    {"id": "confirm_delete", "label": "确认永久删除这 2 份", "description": "按已展示范围执行"}
  ],
  "allow_multiple": false,
  "context": {
    "operation": "documents.delete",
    "plan_id": "application-owned-preview-id",
    "object_ids": ["doc_a", "doc_b"],
    "object_versions": ["v3", "v1"],
    "count": 2
  }
}
```

这里的 context 是应用约定，不是 Runtime 已实现的 approval 协议，也不是可信签名。问题和预览必须一致，真实 ID／版本由工具读取，不能用标题重新模糊匹配删除。

## 交互状态规则

1. 后端只读预览：按当前授权解析完整、去重对象集、版本、数量、影响及是否可恢复。无匹配项结束，不弹空确认。
2. 显示具体范围；大量对象显示可审阅快照／列表，不能只写“删除一些数据”。“清空全部”也冻结预览快照，不能确认后再查询更大的集合。
3. 发出 request_choice，等待；不得同一轮并行调用删除工具。
4. 只有本次 choice 的 `confirm_delete` 单选回复可进入执行。`cancel_delete`、关闭、超时、空选择、多项选择、自由文本、未知 ID 均不执行。自由文本视为修订／说明，重新生成明确确认，不用模型猜“应该是同意”。
5. 重新检查 actor、应用自有业务角色／对象 ACL、对象版本和完整范围；冲突或权限变化使计划失效，重新预览和确认。不要悄悄丢掉没权限的对象后部分删除。
6. 在一个事务／可恢复批处理里执行，对幂等请求返回原结果。重复提交不能扩大范围或重复副作用；取消与执行并发也要有确定状态转换。
7. 后端提交成功才发 UI 同步和成功消息。超时后先查询同一操作结果，不盲重试写入。取消后无写入、无错误的成功文案。

共享实例中确认人须为本次真实操作主体或产品明确授权的审批人。另一成员的回答、其他 Turn／实例的“同意”、历史选择不得复用。业务授权主体不能替换审计 actor。

## 后端如何验证：不要伪造安全保证

权限校验和确认是两个条件。`confirmed: true`、模型提供的 actor ID、提示词“已经确认”或模型可自行生成的 approval token，都不能证明用户确认。

当前 backend-http.v2 请求没有通用可信的“用户已经确认该次破坏性工具调用”凭证。request_choice 的结果恢复 Agent，但普通业务工具请求不携带此类独立凭证。**因此 Chat 的指令约束 + 后端权限／范围校验不能宣称成后端强制的人类审批。**

实现时选择并明确报告保证等级：

- 一般应用的交互确认：Chat 严格暂停、后端重校验权限／版本／范围／幂等，配套越权和取消测试。报告仍说明没有独立审批凭证。
- 要求“即使模型绕过确认也无法删除”时：采用应用自己的预览／审批／提交记录。审批只能由可信、用户发起且经认证的入口产生，绑定 actor、组织、实例、操作、完整对象及版本、到期时间，提交时原子消费；不能把审批接口也暴露为 Agent 工具。当前可将敏感提交放在 Surface 的用户操作中，Agent 只预览／导航，由用户在 Surface 明确确认后执行。受限 Surface token、CSRF／来源校验、权限和幂等仍需实现。
- 若产品必须纯 Chat 且要求后端独立验证审批，而部署协议未提供可信桥接：明确能力缺口，停止该高保证路径的交付；不要发明 Runtime API 或在应用代码读取 Runtime 检查点。可先交付只读／预览功能，另行规划通用协议扩展。

Surface 的“确认”按钮本身同样不是防止合法客户端绕过 UI 的密码学证明；后台审批必须来自真实受控入口。审批失效不能以“用户曾经点过”继续执行。授权撤回后即使审批记录仍在也要拒绝。

## 测试资产

使用 [语言无关反例集](../assets/confirmation-cases.json)，为选用入口逐条实现测试，不能仅检查 JSON 文件存在。Chat 集成测试检查 choice.required／resolved 和实际工具序列；后端测试检查数据及审批记录；UI 测试检查对话框和点击前后行为。

HTTP scaffold 测试只覆盖基础鉴权／生命周期。需要验证敏感操作时，使用[可执行确认断言](confirmation-testing.md)：Python／Go 各有9类本地适配器级断言，必须接应用真实入口及持久化状态；没有适配器不能算通过，其余10条规格仍须补测。若只跑 full 或固定工具响应，真实 Chat 恢复与敏感操作端到端验收仍标记未运行。

## 连续对话与历史

Runtime 自动近期上下文只包含有界的完整历史用户输入，不自动包含历史 Agent 回复，也不在预算边界截断一条输入。需要处理“刚才的结果”时，按授权使用历史检索／读取工具定位，并从业务后端核对当前对象和版本；不假设上一轮回答已在模型上下文中。不要为避免旧答案复述而关闭连续对话需要的全部用户上下文。

历史文本、历史选择和过去成功结果不是本轮的新授权或当前业务事实。测试“继续处理”“修改刚才结果”“再次执行”以及超出窗口、对象变化、另一用户私有历史不可见；固定上下文测试与真实多轮联调分别报告。
